# 0005: 3D physics and view

Plan 0001, migration steps 2 (3D part) and 6 (3D rendering). Port `Particle3D.java` onto the plan 0002/0003 engine, check it bit for bit against the Java app, and draw 3D presets with a perspective view the user can turn.

## Scope

- 3D hard spheres in reflecting, periodic, divided and holed arenas (insulating divider, Maxwell's demon gate): the same arena types 2D supports.
- All 12 3D presets load and run; the preset picker lists them.
- Out of scope, as in 2D: the piston, wells, reactions, thermostat, conducting divider, trace and colour modes (plan 0001 step 8 and the rendering baseline).

## Physics

- `src/sim/particle-3d.ts` ports `Particle3D`: motion, pair prediction (with up to 8 periodic images, checked in Java's order), boundary prediction (walls or periodic boundaries per axis, then the divider, then the edge spheres), the collision response in an orthonormal basis (including Java's fallback when the relative velocity is nearly along the line of centres), and the edge-sphere bounce.
- `Simulation` picks the 2D or 3D particle functions per run and carries z through everything dimension-specific: the event state Java predicted from (`predictionState`), periodic wrap counting, cell crossings, `SetTotalMom` and kinetic energy.
- `CellGrid` gains a z axis (one layer in 2D) and a precomputed per-cell neighbour table (9 or 27 entries). Walking the table instead of nested offset loops kept 2D at its previous speed: the generalized loops had cost 2D about 10–15%.
- `createArena` builds the 3D hole as Java's `ArenaInfo` does: a ring of `round(4π·r/edgeRadius)` spheres, the angle accumulated step by step.
- Java's `PredCol` returns the calling particle's own `t0` for overlapping, approaching spheres; that either equals the pair's time or makes Java throw, so the port returns the pair's time, as in 2D.

## Parity

- `ParityDump` (fork branch `boltzmann4d-parity-tools`) now also dumps the 12 3D presets, with final `z`/`vz`.
- The 3D hole's edge spheres come from `Math.sin`/`Math.cos`. HotSpot's intrinsics differ in the last bit from V8 (and even from Java's own `StrictMath`), which moved one edge sphere by an ulp and changed one `3Deffuse` event time. That is libm noise, not physics, so 3D holed fixtures record Java's ring (`edgeY`/`edgeZ`) and the test passes it in through `InitialState.holeEdges`.
- All 12 3D presets match Java bit for bit: every event and the final state, over the committed 2,000-event fixtures and, checked once by hand, over 20,000 events each.

## View

- `src/render/view-3d.ts`: perspective camera (Java's 30° vertical field of view, widened on portrait screens), lit instanced spheres (Java's 28% ambient + 72% diffuse from a camera-fixed light), the walls as gold/tan panels facing inwards so the near ones never hide the particles, and the divider as a slab with a round hole, a grey tunnel and the ring of edge spheres. Periodic arenas draw up to 8 images per sphere, clipped to the box.
- The camera sits far enough back to fit the sphere around the box. Java's distance puts the front face edge to edge, so turning the box pushed it off screen.
- Turning: drag (mouse, pen or touch) or the arrow keys on the focused canvas, about x then y like Java (`rotateView` action → `SimulationClient.rotate` → renderer). The preset's `3d_viewing_angles` set the starting angles.
- The renderer is now a thin shell over a `View` (`view-2d.ts`, `view-3d.ts`).

## Benchmarks (Apple Silicon, Node 24, `mise run bench`)

Iterations of 1,000 events per second: 2Dmixture ~380, 2Dbrownian ~190 (both unchanged), 3Dmixture ~160, 3Dbrownian ~145.
